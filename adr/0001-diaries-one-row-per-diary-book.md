# 0001. 日記は日記帳ごとに1行で持つ

- 状態: 採用
- 日付: 2026-11-21

## 背景

日記は1回書くと、選んだ日記帳すべてに出せる。テーブルの持ち方には2つの案がある。

- **A. 日記帳ごとに1行（今の設計）**: `diaries` に日記帳の数だけ行を作る。本文は `diary_contents` に1対1で持つ
- **B. 1対多**: 中身を1行だけ作り、どの日記帳に出したかを別のテーブル（`diary_id`, `diary_book_id`）に持つ。記録（投稿）の `posts` と `post_diary_books` と同じ形

日記に写真を付けたとき（2026-11-21）、1枚の写真を複数の行が指すことになり、「どの行も指さなくなったら R2 から消す」仕組みが要った。これをきっかけに、B のほうがよかったかを考え直した。

## 決めたこと

A（日記帳ごとに1行）のままにする。

今の仕様では、日記は日記帳ごとに別のものとして扱う。

- 書くページで日記帳を選んで保存するので、一部の日記帳だけ書き直せる
- リアクション（`diary_reactions`）と通知（`diary_notifications`）は、日記帳ごとの日記に付く。ほかの日記帳のリアクションは見えない
- 本文のロック（その日記帳にその日自分も書いた人だけが読める）は、日記帳ごとに決まる
- 1人1日1件は日記帳ごと（`unique (author_id, diary_book_id, date)`）

## B にしなかった理由

- 一部の日記帳だけ書き直すとき、中身をコピーして分け、その日記帳だけ付け替える処理が要る
- `diary_reactions` と `diary_notifications` のキーに `diary_book_id` を足し、RLS も日記帳のメンバーで絞り直す必要がある
- 本文のロックのポリシーが、出し先のテーブルとの結合を挟む分だけ込み入る
- `author_id` と `date` は中身の側、`diary_book_id` は出し先の側に分かれるので、1日1件を1つの unique 制約で書けない。トリガーか、出し先の側にも同じ値を持たせる工夫が要る

記録（投稿）が B なのは、書き直しがなく、日記帳から外すだけだから。日記とは仕様が違う。

## 結果

良いこと

- 書き直し、リアクション、通知、本文のロックが、日記帳ごとの行に対してそのまま書ける
- 1日1件を1つの unique 制約で守れる

困ること

- 同じ本文が日記帳の数だけ入る。日記は1日1件で使うのも身内だけなので、量は問題にならない
- 保存のとき、日記帳の数だけ `save_diary` を呼ぶ
- 1回で上げた写真を複数の行が同じパスで指す。そのため、どの行も指さなくなってから消すトリガー（`delete_unused_diary_photos`）と Edge Function（`delete-diary-photos`）を作った。詳しくは `docs/diary_photo.md`

## 見直すとき

「同じ日に書いた日記は、どの日記帳でも常に同じ中身」に仕様を変えるなら、B に移すことを考える。リアクションも日記帳をまたいで共有するなら、なおさら B のほうが合う。
